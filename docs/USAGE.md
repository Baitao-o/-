# 麦门省钱搭子 使用说明

## 1. 这是什么

麦门省钱搭子是一个基于麦当劳 MCP 的命令行点餐助手：给它人数、预算和口味偏好，它调用真实门店数据，输出 2~3 套可解释的点餐组合，或按你要求的结构算出最低价组合。

## 2. 准备工作

- Python 3.8+
- 麦当劳 MCP Token（获取步骤见下）
- 能访问 `https://mcp.mcd.cn` 的网络

### 获取麦当劳 MCP Token

1. 打开 [open.mcd.cn/mcp](https://open.mcd.cn/mcp)；
2. 点击右上角「登录」，用手机号验证码登录；
3. 登录成功后点击右上角「控制台」；
4. 点击「激活」按钮，阅读并同意服务协议；
5. 申请成功后一键复制 MCP Token。

### 配置 Token（环境变量 `MCD_MCP_TOKEN`）

程序从环境变量 `MCD_MCP_TOKEN` 读取 Token，请把 `你的Token` 替换成真实值：

**Windows（PowerShell，当前窗口有效）：**

```powershell
$env:MCD_MCP_TOKEN = "你的Token"
```

**macOS / Linux（当前终端有效）：**

```bash
export MCD_MCP_TOKEN="你的Token"
```

> Token 属于敏感凭据，不要提交到 Git 仓库、截图或公开文档。

## 4. 两种用法

### 4.1 默认模式：给预算，出 2~3 个方案

只给人数和预算，系统自动在「最省钱 / 均衡饱腹 / 丰富尝鲜」三个侧重上各出一套方案，并给出首选推荐：

```bash
python src/meal_planner.py --people 2 --budget 130 --mode pickup --city 绍兴 --keyword 上虞
```

输出见第 3 节。可选增强：

- `--no-spicy`：不吃辣；
- `--avoid 咖啡,香菜`：忌口关键词（逗号分隔）；
- `--want-dessert`：希望带甜品；
- `--no-drink`：不需要饮料。

### 4.2 结构模式：给预算 + 餐品结构，出最低价组合

这是本作品最有辨识度的功能：你指定「主食/小吃/甜品/饮品各要几份」，系统在该结构下**求实付总价最低的组合**，而不是泛泛的“推荐”。所有份数必须完全满足，且逐个候选商品调用真实算价校准。

```bash
python src/meal_planner.py --budget 100 --main 1 --snack 1 --dessert 1 --drink 1 --mode pickup --city 绍兴 --keyword 上虞
```

真实输出：

```text
（已按品类校准 1 个商品的真实单价）

✅ 符合该结构的**最低价组合**：实付 ¥35.00，预算内还余 ¥65.00

- **主食 1 份**：牛肉堡单品精选　¥13.50/份　小计 ¥13.50
- **小吃 1 份**：苹果片　¥7.00/份　小计 ¥7.00
- **甜品 1 份**：灰焰圆筒　¥5.00/份　小计 ¥5.00
- **饮品 1 份**：雪碧　¥9.50/份　小计 ¥9.50

以上为该门店**当前可售、符合结构、总价最低**的组合；如需更便宜可减少份数或提高预算档位对比。

```

三个值得注意的技术点：

1. **菜单价不等于成交价。** 菜单里的 `currentPrice` 可能只是「最低价起售」（实测某四件套菜单标 ¥28、实际下单 ¥52），所以程序会对候选商品逐个调用 MCP 的真实算价能力校准单价，再参与求解。
2. **求的是“最低价”而非“推荐”。** 结构份数是硬性要求，系统在满足全部份数的前提下找实付最低的组合，并把价格依据（算价校准、预算余量）完整展示。
3. **硬约束不可违反。** 预算内配不齐时，程序会如实告诉你最低需要多少钱，不会硬凑一个超预算方案（示例见第 7 节）。

份数默认是「总份数」；加 `--per-person` 则按人数翻倍（例如 `--people 4 --main 1 --per-person` 表示每人 1 份主食、共 4 份）。

### 4.3 可视化界面（网页版）

不想敲命令行时，可以起一个本地网页界面。**零依赖**，只用 Python 标准库：

```bash
python web/server.py
# 浏览器打开 http://127.0.0.1:8808
```

界面上可以直接：

- 填预算与人数；
- 选「到店自取 / 麦乐送」；
- 用步进器设置「主食 / 小吃 / 甜品 / 饮品」各几份（0 表示不要）；
- 勾选「每人一份」「不吃辣」，填忌口关键词；
- 点一次按钮出结果。

结果页展示：门店信息、按品类分组的商品明细、实付总价、预算剩余进度条、费用拆分。
适合录屏演示（赛事要求「使用说明或录屏」）。

可选环境变量：`PORT`（默认 8808）、`HOST`（默认 127.0.0.1）、`OPEN_BROWSER=0`（不自动开浏览器）。

网页与命令行**共用同一套** `src/meal_planner.py`，因此结果一致；
接口为 `POST /api/plan`，结构份数为 0 时自动退回「默认模式」返回 2~3 个方案。

## 5. 对话式使用示例

命令行之外，这个 Skill 也可以在 WorkBuddy 对话中直接使用。以下两个往返示例体现它对含糊表达的理解、对缺失字段的追问和对硬约束的坚持。

### 示例 1：含糊表达 + 追问缺失字段

**用户：**

> 帮我点麦当劳，我们几个人随便吃点，别太贵。

**Skill：**

> 为了给你算得准，需要两个信息：一共几个人吃、预算大概多少？如果想指定门店（比如附近的某个麦当劳），也一起告诉我。
>
> 另外确认一下：「别太贵」我按人均 30~50 元理解可以吗？如果你们有忌口（比如不吃辣、不要咖啡）也一并说。

**用户：**

> 4 个人，一共 150 吧，两个人不吃辣。

**Skill：**

> 我根据 4 人、预算 ¥150、不吃辣查到以下方案（真实运行结果，门店「麦当劳绍兴上虞上百万悦城餐厅」）：
>
> 方案 A｜最省钱
> - 龙焰鸡腿堡 ×4（¥16）
> - 苹果片（¥7）
> - 鲜萃咖啡 ×4（¥10）
> - 派 ×4（¥8）
> - 预计总价：¥144.60　人均：¥36.15
> - 费用拆分：商品 ¥144.60 + 优惠 −¥32.40
>
> 方案 B｜均衡饱腹
> - 枫糖风味厚松饼猪柳堡三件套 ×4（¥24）
> - 薄皮焦香V翅（¥16）
> - 雪碧 ×4（¥10）
> - 预计总价：¥149.10　人均：¥37.27
>
> 我的首选：方案 A —— 总价 ¥144.60 在预算内，人均 ¥36.15，
> 且同时带甜品与饮品，13 件分的份量对 4 个人也够。
>
> 你可以回复「选 A」「把咖啡换成可乐」或「查看下单清单」。

> 复现命令：
> `python src/meal_planner.py --people 4 --budget 150 --mode pickup --city 绍兴 --keyword 上虞 --no-spicy`
>

### 示例 2：硬约束被违反时如实拒绝

**用户：**

> 20 块钱，帮我配 2 个主食加 2 个小吃。

**Skill：**

> 无法按该结构出方案：按该结构的最低商品总价约 ¥41.00，已超出预算 ¥20；请提高预算或减少份数。

**用户：**

> 那最少要多少钱？

**Skill：**

> 按「主食 2 份 + 小吃 2 份」在该门店当前可售商品中的最低组合，约需 ¥41（例如：汉堡单品 ¥13.5 ×2 + 小食 ¥7 ×2 一类组合）。你可以把预算提到 ¥45 左右留点余量，或者改成「主食 1 份 + 小吃 1 份」这样 ¥25 以内就能拿下。

Skill 不会硬凑一个超预算的方案，也不会悄悄减少份数来“假装”满足预算。

## 7. 常见问题

**Q：报 Token 相关错误怎么办？**
确认已设置环境变量 `MCD_MCP_TOKEN` 且值完整（没有多余空格或引号）；确认 Token 在麦当劳控制台仍然有效；Token 泄露或失效时到 open.mcd.cn/mcp 控制台重新生成。

**Q：门店查不到怎么办？**
检查 `--city` 与 `--keyword` 拼写；换更具体的关键词（如商圈、商场名）；或用 `--store` 直接指定门店编码。

**Q：预算内无解怎么办？**
程序会如实输出最低所需金额（如第 5 节示例），请提高预算或减少份数；默认模式下也可以减少人数约束。

**Q：外送和到店价格为什么不一样？**
不同服务方式的定价与可用优惠可能不同，结果以对应 `--mode` 的真实返回为准；对比价格请固定同一 `--mode`。

**Q：输出价格和下单页不一致？**
价格与可售状态实时变化，输出中的价格来自 MCP 当时返回并经算价校准，最终以下单页面为准。

## 8. 已知限制

- 部分商品菜单价是「最低价起售」，程序已通过真实算价校准，但仍以下单页为准；
- 优惠券叠加未做全量求解，当前按接口返回的可用优惠计算；
- 依赖麦当劳 MCP 客户端接口，非官方开放 API，接口变化可能影响功能；
- 营养、过敏原等信息以官方返回为准，程序不做医疗建议；
- 不自动支付，真实下单需在客户端确认。
- 网页版为本地单机界面，未做多用户鉴权与部署适配；如需公网演示，建议只录屏不给实时访问。
